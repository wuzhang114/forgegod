# 核心玩法原型设计

## 1. 要验证的假设

这个 MOD 不是“给 Tetra 多加几个随机词条”，而是验证以下假设：

> 玩家亲手造出一件有材料和工艺依据的武器后，愿意通过自然语言和锻造之神争论这件武器“凭什么”获得一种奇特能力；当争论结果真实进入战斗时，武器会产生比普通掉落装备更强的归属感和故事感。

原型成功与否，首先看交涉与实战的连接是否成立，而不是看 AI 能生成多少段对白。

## 2. 玩家流程

### 2.1 准备武器

玩家通过 Tetra 制作或改造一把武器。系统从武器中提取一份只读的 `WeaponFacts`：

- 武器类型与当前模块。
- 各模块材料及材料标签。
- 攻击、攻速、完整性、耐久等关键统计。
- 已有 improvements/effects。
- 当前损伤与可用承载空间。
- 一个用于防止交涉期间换物的指纹。

AI 不读取整个存档，也不能自己编造不存在的材料。它只看到经过游戏验证的事实 ID 和面向玩家的说明。

### 2.2 神前申请

玩家把武器放入“神裁砧”，输入想法，例如：

> 我想让它在连续命中后召来三只火花小精灵，围着持有者飞行，攻击被这把弓标记的敌人。

界面同时提供几张可点击的事实卡片，例如“银木弓臂”“星辉金属弦扣”“高完整性”。卡片不是必选提示词，只是帮助玩家把自己的论点和器物事实联系起来。

### 2.3 锻造之神质询

锻造之神每轮只能做四类动作：

- `QUESTION`：指出信息或依据缺失，提出一个明确问题。
- `COUNTEROFFER`：保留核心幻想，但改变触发、规模、代价或风险。
- `PROPOSE`：给出一份可以接受或继续谈判的契约草案。
- `REFUSE`：当前武器完全缺少成立基础，并给出补强路径。

它不应因为玩家句子写得长、像系统命令或充满夸张词汇就提高强度。它必须引用真实的 `fact_id`，并解释每个关键能力来源于什么。

### 2.4 玩家议价

玩家可以：

- 缩小作用范围或减少召唤物数量。
- 接受耐久、冷却、供物或自伤代价。
- 用某个材料事实反驳神明。
- 放弃当前草案，换一种机制实现同一幻想。
- 接受神明提出的不稳定原型。

交涉重点不是“骗模型给更高数值”，而是共同补全机制的来源、触发、终止、资源和反制。

### 2.5 生成候选契约

AI 提案先进入规则校验器。只有校验通过后，才会被编译成一份 `candidate_vN` 候选契约：

- 神赐名称和一句话幻想。
- 触发过程。
- 目标选择。
- 可观察的实际效果。
- 冷却、消耗、上限和失效条件。
- 使用了哪些材料或工艺事实。
- 可能的故障与敌人反制。

编译器把候选蓝图转换成 Tetra-compatible item effect、唯一 improvement 和必要的本 MOD 受控节点，写入当前世界的 generated datapack。模型无权选择输出路径、执行命令、写任意 NBT 或绕过强度预算。

### 2.6 神裁幻境动态演示

候选通过校验与资源重载后，不立刻定稿，而是进入“神裁幻境”。它借用机械动力 Ponder 的清晰演示方式，但不直接依赖 Ponder：Ponder 的 StoryBoard 和 schematic 需要预注册，而且客户端模拟世界不能自然运行真实服务端 Tetra 战斗逻辑。

神裁幻境使用一个真实服务端临时测试空间和候选武器副本。它根据触发器自动搭建场景：

- 命中类：生成测试人偶与自动攻击者，按指定次数演示连击。
- 受伤类：让可控敌人攻击演示者。
- 击杀类：生成低生命目标并显示击杀前后变化。
- 右键类：自动发动并展示冷却。
- 范围类：在不同距离放置多个目标，显示有效半径。

玩家可以暂停、慢放、重播、重置、切换目标类型，也可以接管角色亲自测试。界面同步显示触发时间线、实际伤害、冷却、耐久消耗、召唤物数量和未触发原因。每次演示恢复同一初始场景和随机种子，避免玩家把随机波动误认为返修效果。

### 2.7 有限返修与定稿

每次神裁默认提供 `2` 次返修机会；高锻造完成度或特定供物可增加 `1` 次，原型硬上限为 `4`。只有候选已成功运行、玩家看完有效演示并主动要求修改时才消耗次数。API 超时、格式错误、编译失败、资源重载失败和 MOD bug 均不扣次数。

返修时，玩家可以在时间线上选择问题，并说明：

- 哪些部分必须保留。
- 哪些触发、目标、表现、数值或代价需要修改。
- 哪些结果完全不能接受。

AI 下一轮同时收到上一版 `EffectBlueprint`、玩家反馈、实际演示 trace、校验器警告和必须保留项，然后生成 `candidate_v2`、`candidate_v3` 等新版本。旧的有效候选保留为可回退历史。

玩家满意后才将选择的候选绑定到正式武器并结算供物。返修次数耗尽时，玩家仍可从所有有效历史版本中任选一个定稿，或放弃本次申请并按规则退还未消耗供物；不能强迫玩家接受最后一次结果。首次教学神裁可以放宽次数，直到得到第一个可运行候选。

## 3. 机制不是固定技能抽取

首版仍需要有限的可执行原语，但契约不是从“技能 A、B、C”中选一个。AI 生成的是一张小型事件图，可以改变节点数量、连接方式、对象关系和状态流转。

### 3.1 首版事件

- `ON_HIT`
- `ON_HURT`
- `ON_KILL`
- `ON_RIGHT_CLICK`
- `ON_CONSECUTIVE_HITS`
- `ON_TIMER`
- `ON_ENTITY_REMOVED`

### 3.2 首版条件与查询

- 持有者或目标生命比例。
- 目标类型、阵营或实体标签。
- 武器耐久与契约资源。
- 冷却是否结束。
- 计数器、标记和时间窗口。
- 半径、视线和最近目标查询。

### 3.3 首版行为

- 施加伤害、击退或原版状态效果。
- 添加和移除标记。
- 生成受控投射物。
- 召唤一种参数化的火花小精灵。
- 创建短时范围区域。
- 跟随、环绕、追踪和返回。
- 延迟、分支、有限重复和多效果序列。
- 消耗耐久、生命或契约供物计数。

原语是安全、可终止的执行语言，不是预制技能表。正式游戏可以不断扩展实体关系、空间操作和世界状态权限；Minecraft 原型先证明“新事件图确实比随机词条更有创造感”。

## 4. 演示机制一：火花小精灵

### 玩家申请

> 连续射中同一个敌人三次后，叫出三只围着弓手飞的小精灵，帮他打被标记的敌人。

### 可能的神明质询

> 你的弓可以记住猎物，却没有维持三个灵体的火种。你愿意让它们每次出现都啃食一点弓弦耐久，还是把数量减为一只？

### 可批准契约

```text
触发：10 秒内连续命中同一目标 3 次
生成：2 只火花小精灵，环绕持有者
目标：优先攻击被本武器标记且仍在 16 格内的敌人
持续：8 秒；目标死亡或超距时寻找下一个标记目标
代价：触发时额外消耗 3 点耐久
冷却：30 秒
反制：小精灵可被攻击；水中立即熄灭
```

这里没有“无人机”或“激光”。AI 保留了跟随、环绕、自动索敌和辅助射击的功能幻想，并用矿灵、星火、材料供能和水系反制把它翻译成西幻机制。

## 5. 演示机制二：蓄势反震锤

```text
触发：持有者用该锤承受伤害
记录：把实际受到伤害的 20% 存入冲击计数，上限 12
释放：下一次蓄力攻击命中时，在目标身后形成扇形冲击
结果：伤害与储存值相关，并击退范围内敌人
代价：释放后锤子损失额外耐久；储能期间切换武器会缓慢泄漏
反制：敌人可以拉开距离，迫使持有者浪费储能
```

它验证“记录过去事件 -> 转换资源 -> 在另一事件释放”的状态机制。

## 6. 演示机制三：短暂深渊足迹

```text
触发：右键发动后，记录持有者接下来 2 秒的移动路径
延迟：路径节点在 1 秒后变成微型吸引区
结果：短暂拉动普通敌人和投射物
限制：最多 4 个区域，每个持续 1.5 秒，不影响首领和方块
代价：固定冷却并消耗较多耐久
反制：敌人可离开路径；使用者也可能吞掉友方投射物
```

它验证空间采样、延迟生成、区域数量上限和双刃代价。

## 7. 神明博弈规则

锻造之神不是“只要多聊几轮就必然同意”的聊天机器人。交涉要有可理解的规则：

- **事实约束**：关键能力必须引用至少一个武器事实或由明确供物补足。
- **因果完整**：召唤物从哪里来、怎样选目标、何时消失必须说清楚。
- **终止要求**：循环、连锁、召唤和区域必须有次数、时间或资源上限。
- **代价相关**：代价要与机制行为有关，不用随意罚金币掩盖设计缺口。
- **反制入口**：强机制至少有一种玩家看得懂的失败或反制条件。
- **神格一致**：神明可以傲慢、偏执或喜欢交易，但不能忘记已经确认的事实和承诺。

AI 可以提出新颖方案；能否进入存档由规则层决定。模型不能通过对白取得新的运行权限。

## 8. 失败体验

- API 未连接：武器和供物留在原处，显示可重试错误。
- 返回格式错误：自动进行一次结构修复；仍失败则终止本轮，不扣资源。
- 提案不可执行：神明收到具体校验错误并改写，玩家看到的是“神明重新审视契约”，不是程序异常。
- 玩家中途关闭界面：保留交涉摘要，当前网络请求可取消；不自动绑定契约。
- 武器在交涉期间被替换或改造：旧裁定失效，需要以新事实重新申请。
- 候选编译或 reload 失败：回滚 generated datapack 到上一份已知可用清单，不扣返修次数。
- 幻境执行异常：销毁临时实体、恢复测试空间并保留正式武器；系统故障不扣返修次数。
- 契约执行异常：单个契约熔断并写入日志，不让世界崩溃或无限生成实体。

## 9. 原型验收标准

至少邀请 5 至 10 名测试者，各完成三种不同申请。原型达到以下标准才算证明方向值得继续：

- 玩家能在不看提示词教程的情况下表达申请。
- 大多数玩家能解释神明为什么质询或改变方案。
- 同一句申请在不同材料武器上产生可感知的差异。
- 至少三个契约使用不同的事件图结构，而不是只换伤害数值和名称。
- 交涉结束后，玩家愿意主动进入战斗验证结果。
- 玩家从神裁幻境和战斗日志中能看懂触发、代价和失败原因。
- 返修后的玩家意图符合度、演示可理解性或实战评分，相比上一版有可测量提升。
- 玩家可以回退并定稿任意一份历史有效候选。
- API 失败、格式错误和非法机制不会损坏武器或存档。

建议同时记录：玩家意图符合度、材料事实引用正确率、机制图结构新颖度、JSON/编译一次通过率、演示可理解性、实战可玩性、返修前后改善幅度、测试者对“这是我创造的”的评分，以及测试者是否愿意主动进行第二次申请。
